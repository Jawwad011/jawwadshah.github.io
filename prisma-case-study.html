CASE STUDY • 03

PRISMA Follow-up Dashboard

A Flask and SQL Server-based internal application designed to monitor research follow-ups, form status, synchronization and operational data.

Python Flask SQL Server HTML/CSS Jinja

THE PROBLEM

Making follow-up data easier to monitor.

Research follow-up information was distributed across multiple forms and database tables.

Teams needed a centralized interface to identify follow-ups, understand their current status and monitor synchronization information.

The application also needed to support controlled updates to follow-up information while maintaining an audit trail.

APPLICATION ARCHITECTURE

Connecting the database, backend and interface.

01

SQL Server

Stores follow-up and form information used by the application.

→
02

Flask Backend

Handles routes, database queries, validation and application logic.

→
03

Web Interface

Provides searchable and filterable views for users.

DEVELOPMENT APPROACH

From SQL queries to a working application.

01

Data Layer

Designed SQL queries and database views to retrieve the required follow-up information.

02

Flask Backend

Connected the application to SQL Server and implemented routes for searching, filtering and processing records.

03

Business Logic

Implemented follow-up status, visit logic, permissions and controlled update workflows.

04

User Interface

Built HTML and Jinja templates to provide users with a clear and practical interface.

KEY FEATURES

Built around real operational requirements.

Search & Filtering

Users can locate relevant follow-up records using identifiers and form-related filters.

Follow-up Status

Application logic determines and displays relevant follow-up and synchronization status.

Controlled Updates

Follow-up information can be updated through controlled application workflows rather than directly editing database records.

Audit Trail

Changes can be tracked with previous values, new values, reason and user information.

TECHNICAL IMPLEMENTATION

SQL Server and Flask working together.

SQL + Flask

SQL Server provided the data layer while Flask handled application routing, business logic and interaction with the database.

Jinja templates were used to render dynamic data into the web interface, creating a lightweight internal application without requiring a large frontend framework.

OUTCOME

Turning database operations into a usable application.

Centralized Monitoring

Follow-up information could be viewed through a centralized interface.

Controlled Data Updates

Updates could be handled through defined application workflows and permissions.

Better Operational Visibility

Users could more easily identify follow-up status and records requiring attention.
